## Phase 8.0 总览

你已完成 Phase 0-5，有了一个**完整的最小 Agent 框架**。Phase 8 的目标是让它「好用、可衡量、可扩展」。

### 为什么要有这些进阶能力

| 缺什么 | 做了之后 |
|--------|---------|
| 改了 prompt 不知道变好还是变差 | 评测框架量化能力变化 |
| 模型写死，换模型要改代码 | 一行配置切换厂商 |
| 不知道一次任务花多少钱 | 成本面板 + 用量统计 |
| 工具只能写死在代码里 | 接入 MCP，社区工具即插即用 |
| 大任务 Agent 一个人干容易乱 | 子代理拆开并行干 |


## Phase 8.1 评测框架 Eval

**目标**：建立 benchmark 任务集，每次改动后跑一遍，量化 Agent 能力变化。

**你将学到**：Agent 评测方法论、评分标准设计、回归检测。

### 为什么最先做

这是所有后续改动的「度量衡」。没有评测，改 prompt、换模型、加工具，你都只能「感觉好像变好了」。有了评测，每次改动都有数据支撑。

**关键**：Eval 完全不依赖 Phase 8 的其他特性，用现有 Phase 0-5 代码就能直接做。

### 核心设计

整个评测系统分三层：

1. **任务集**：一组有标准答案的任务定义。每个任务包含：任务描述、验证方式、难度等级。
2. **执行器**：逐个把任务发给 Agent 跑，收集 Agent 的输出。
3. **评分 + 报告**：用预定义的规则验证 Agent 输出是否正确，生成通过率、得分、耗时、成本等统计。

### 三种验证方式

| 方式 | 适用场景 | 怎么判断对错 |
|------|---------|-------------|
| **contains** | 答案是确定性的（如"项目名是什么"） | 输出里包含预期字符串就算对 |
| **script** | 需要运行代码验证（如"创建了文件没有"） | 跑一个验证脚本，退出码 0 = 通过 |
| **model-graded** | 开放式问题（如"总结得好不好"） | 用另一个模型打分 |

**建议先实现 contains 和 script 两种**，model-graded 比较复杂可以以后再加。

### 关键设计决策

**评测时权限怎么处理？**

评测要全自动跑，不能每个写文件操作都停下来问用户。你需要给安全审批器加一个「自动批准模式」：评测时所有工具调用自动 allow（或者只 allow 只读类工具）。

> 这是唯一需要改现有代码的地方：在 `SafetyOptions` 里加一个 `autoApprove` 字段，approver 看到这个字段就直接返回结果，不走交互式审批。

**token 和成本怎么算？**

用你已有的 `estimateMessagesTokens` 估算总 token，乘以模型单价算成本。不需要精确，数量级对就行。

**基线对比怎么做？**

第一次跑完评测后，把报告存为 `baseline.json`。以后每次跑完，和基线对比：哪些任务进步了、哪些退步了。这叫**回归检测**。

### 实现步骤清单

1. 定义 `EvalTask`、`EvalResult`、`EvalReport` 三个类型
2. 写价格估算模块（维护一个模型→单价的映射表）
3. 写评测执行器：循环跑任务 → 调 `runAgent` → 验证输出
4. 给 approver 加自动批准模式（`autoApprove: "allow" | "deny"`）
5. 写报告生成器：格式化输出 + 基线对比
6. 创建 5-6 个评测任务（基于你已有的 read-file / list-dir 工具）
7. 在 CLI 加 `eval` 命令
8. 跑第一次，保存为基线

### 评测任务设计建议

设计任务时注意覆盖不同维度：

| 维度 | 示例任务 |
|------|---------|
| 单工具调用 | 读取 package.json，说出项目名 |
| 多步推理 | 先读 A 文件，再读 B 文件，比较内容 |
| 工具链 | 读取文件 → 分析 → 给出结论 |
| 边界情况 | 搜索一个不存在的关键词，看 Agent 怎么处理 |
| 写操作 | 创建文件 → 读回来验证内容一致 |

**难度分级**（1-5）：1 = 单步只读，5 = 多步推理 + 写操作 + 需要理解代码结构。

### 验收标准

- [ ] 至少 5 个评测任务，覆盖不同难度和不同工具
- [ ] `pnpm dev eval` 能自动跑完所有任务并生成报告
- [ ] 报告包含：通过率、平均得分、总耗时、总 token、估算花费
- [ ] 有基线后，再次运行能对比出进步和回归
- [ ] 故意改坏系统提示词，评测能检测到通过率下降

### 以后可以做的进阶

- model-graded 验证（用强模型评判开放式回答）
- 按 category 分组统计（看哪类任务弱）
- CI 集成（PR 自动跑评测）
- 难度加权总分

## Phase 8.2 多 Provider 抽象

**目标**：把写死的模型调用抽成 Provider 接口，配置即切换模型厂商。

**你将学到**：接口抽象设计、工厂模式、策略模式。

### 为什么做

现在你的模型调用代码直接从 config 读配置然后 fetch。想换 Qwen、用本地 Ollama、或者不同任务用不同模型，都得改代码。

Provider 抽象的核心思想：**Agent Loop 只依赖接口，不依赖具体实现**。切换模型只改配置，不改代码。

### 核心设计

```
┌─────────────┐
│  Agent Loop │   ← 只依赖 Provider 接口
└──────┬──────┘
       │
       ▼
┌─────────────────┐
│ Provider 接口     │
│ - chat()         │
│ - streamChat()   │
└────────┬─────────┘
         │
   ┌─────┼─────┐
   ▼     ▼     ▼
 OpenAI  Qwen  Ollama  ...
```

### 接口设计要点

Provider 接口需要定义：

- **chat**：非流式调用，传入消息列表 + 工具列表，返回内容 + 工具调用 + token 用量
- **streamChat**：流式调用，异步迭代器逐个产出 delta（文本片段 / 工具调用片段）
- **model**：只读属性，返回模型标识名

**关键**：`chat` 的返回值要包含 `usage`（token 统计），这是 Phase 8.3 可观测性的数据来源。如果某个模型 API 不返回 usage，就用 token 估算兜底。

### 实现步骤清单

1. 定义 `Provider` 接口和相关类型（ChatMessage、ChatTool、ChatResult 等）
2. 把现有的 openai.ts 从「一堆函数」改成「实现 Provider 接口的类」
3. 创建 Provider 工厂函数：根据配置创建对应实现
4. 改 config.ts，加上 provider 类型字段
5. 改 Agent Loop：接收 `provider` 参数，不再直接 import openai.ts
6. 改入口 index.ts：用工厂创建 Provider，传给 runAgent
7. （可选）加一个 Ollama Provider 验证抽象是否正确

### 关键约束

- `loop.ts` 里**不能**出现 `import openai.ts`，只能 `import provider/types.ts`
- 新增一个 Provider 实现，只需要：加一个文件 + 在 factory 加一个 case，**Agent Loop 一行都不用改**
- `ChatMessage` 类型应该从 config.ts 移到 provider/types.ts（它本质是 Provider 层概念）

### 验收标准

- [ ] 改 `.env` 里的模型名，Agent 正常工作，代码一行不改
- [ ] loop.ts 不直接 import 任何具体 Provider 实现
- [ ] 新增 Provider 实现只需加文件 + factory 加 case

## Phase 8.3 成本与可观测性

**目标**：追踪每次运行的 token 用量、花费、每轮耗时、工具调用情况。

**你将学到**：指标收集模式、结构化日志、性能剖析。

### 前置依赖

需要先完成 **8.2 多 Provider 抽象**（usage 数据来自 Provider 层）。

### 为什么做

Agent 跑一次可能 10 轮模型调用 + 20 个工具调用。你需要知道：

- 花了多少钱？
- 哪步最慢？模型推理还是工具执行？
- 哪个工具调用最多？
- 失败率多少？

没有这些数据，优化全靠猜。

### 核心设计

在 Agent Loop 的关键节点埋点，用 TelemetryCollector 收集，最后汇总成运行报告。

```
Agent Loop 各轮:
  轮开始 → 模型调用 → 工具调用×N → 轮结束
    │          │          │
    └── 埋点 ──┴──────────┘
              │
              ▼
        TelemetryCollector
              │
              ▼
          运行报告
```

### 三层指标结构

**TurnMetrics（单轮指标）**：每轮模型调用的耗时、token 数、本轮调了哪些工具。

**ToolCallMetrics（单次工具调用）**：工具名、耗时、成功与否、安全审批结果。

**RunMetrics（整体运行指标）**：总耗时、总轮数、总 token、总花费、工具调用总数、是否成功。

### 埋点位置

| 位置 | 记录什么 |
|------|---------|
| 每轮开始 | 轮号、开始时间 |
| 模型调用前后 | 模型耗时、prompt/completion tokens |
| 每个工具调用前后 | 工具名、耗时、成功与否、安全决策 |
| 每轮结束 | 本轮总耗时 |
| 整体结束 | 总耗时、是否成功 |

### 成本计算

复用 8.1 Eval 里的 pricing 模块。用 Provider 返回的 usage（精确值），如果没有就用 token 估算。

### 报告输出

每次任务结束后在 CLI 打印一个简洁报告：

- 总耗时、模型轮数、工具调用次数
- Token 用量（prompt + completion）
- 估算花费
- 最慢的 3 个工具调用（帮你定位瓶颈）

### 实现步骤清单

1. 定义 `RunMetrics`、`TurnMetrics`、`ToolCallMetrics` 类型
2. 写 TelemetryCollector 类（startTurn / endTurn / startModelCall / endModelCall / startToolCall / endToolCall / finish）
3. 把 collector 接入 Agent Loop（LoopOptions 加 telemetry 参数，在各埋点位置调用）
4. AgentResult 加上 metrics 字段
5. 在 CLI 打印运行报告

### 验收标准

- [ ] 任务结束后看到运行报告：总耗时、轮数、token、花费
- [ ] 报告显示最慢的 3 个工具调用
- [ ] 花费估算和实际账单在同一数量级
- [ ] 任务失败时也能输出报告

## Phase 8.4 MCP 协议支持

**目标**：接入 MCP，让任何 MCP 服务器的工具即插即用。

**你将学到**：MCP 协议原理、Stdio 子进程通信、工具动态注册、JSON-RPC。

### 什么是 MCP

MCP（Model Context Protocol）是一个开放协议，让 AI 模型安全访问外部工具和数据：

- **MCP 服务器**：提供工具的一方（文件系统 MCP、GitHub MCP、数据库 MCP 等）
- **MCP 客户端**：使用工具的一方（你的 Agent Harness）
- 通信方式：JSON-RPC over Stdio（子进程）或 HTTP

接入后，社区现成的 MCP 服务器直接就能用，你不用自己写各种工具。

### 核心设计

```
┌──────────────┐
│  Agent Loop  │
└──────┬───────┘
       │
       ▼
┌──────────────┐    JSON-RPC over Stdio    ┌──────────────┐
│  Tool 注册表  │ ◄──────────────────────► │  MCP 服务器  │
│ (本地+MCP)   │                           │ (外部进程)   │
└──────────────┘                           └──────────────┘
```

**关键设计**：MCP 工具和本地工具最终都注册到同一个 ToolRegistry，Agent Loop 完全感知不到区别。

### MCP 协议三个核心消息

| 客户端 → 服务器 | 作用 |
|-----------------|------|
| `initialize` | 握手，协商协议版本和能力 |
| `tools/list` | 获取服务器提供的所有工具 |
| `tools/call` | 调用一个具体工具 |

### 实现要点

**MCP 客户端**：启动子进程，通过 stdin/stdout 收发 JSON-RPC 消息。需要处理：进程启动、握手、请求-响应匹配（用 id 关联）、缓冲区拼接（消息按行分割）。

**工具适配器**：MCP 工具的接口和你本地的 Tool 不一样，需要一个适配器把 MCP 工具包装成本地 Tool。关键点：
- 工具名加 `mcp__` 前缀，避免和本地工具重名
- MCP 返回的 content 是数组（可能有 text、image），需要提取文本部分

**配置**：在 .env 里配 MCP_SERVERS，格式如 `name:command args`，支持多个（分号分隔）。

**安全策略**：MCP 工具默认走 `ask` 策略（你不知道外部工具会做什么），需要用户确认。

### 实现步骤清单

1. 了解 MCP 协议的三个核心消息
2. 写 MCP 客户端（spawn 子进程 + JSON-RPC 通信 + 请求响应匹配）
3. 写工具适配器（MCP 工具 → 本地 Tool 接口）
4. 在 config 加 MCP_SERVERS 配置解析
5. 在入口启动 MCP 服务器、注册工具
6. 安全策略适配 MCP 工具（默认 ask）

### 验收标准

- [ ] 配置一个 MCP 服务器（如 filesystem MCP），工具列表里能看到它的工具
- [ ] Agent 调用 MCP 工具流程和本地工具完全一样
- [ ] MCP 服务器关掉后，调用返回错误但不崩溃
- [ ] MCP 工具默认走 ask 权限策略

## Phase 8.5 子代理与任务分解

**目标**：主 Agent 把复杂任务拆成子任务，派发子 Agent 并行执行，汇总结果。

**你将学到**：任务分解模式、子代理编排、结果聚合、并行控制。

### 前置依赖

- **8.2 多 Provider 抽象**（子 Agent 要调模型）
- **8.3 可观测性**（可选，但能看到子代理开销）

### 为什么做

单个 Agent 处理复杂任务容易「顾此失彼」——同时改 5 个文件，改到第 3 个就忘了第 1 个的上下文。

子代理 = 项目经理 + 多个工程师：
- 主 Agent：理解任务、拆分子任务、分配、汇总
- 子 Agent：执行具体小任务，各管各的

### 核心设计

```
用户任务
   │
   ▼
主 Agent ── 分解 ──► 子任务列表 [A, B, C]
   │
   ├──────┬──────┐
   ▼      ▼      ▼
 子A    子B    子C    并行执行
   │      │      │
   └──────┼──────┘
          ▼
   结果汇总 → 最终答案
```

### 四个核心组件

**1. 任务分解器**：用专门的 system prompt 让模型把大任务拆成 2-8 个子任务。每个子任务包含：标题、详细描述、依赖关系（依赖哪些前置任务）。要求模型只返回 JSON。

**2. 子 Agent 执行器**：每个子任务由一个独立子 Agent 执行。复用已有的 `runAgent`，但：独立消息历史（不污染主 Agent）、可限制可用工具、最大轮数少一些（子任务不需要太多轮）。

**3. 编排器**：按依赖关系执行子任务。核心是拓扑排序 + 有限并行：
- 没有依赖的子任务可以同时跑（控制最大并行数，如 2-3）
- 有依赖的等前置完成后再跑
- 把已完成子任务的结果作为上下文传给后续子任务

**4. 结果汇总器**：所有子任务完成后，用另一个专门的 prompt 让模型汇总成一个最终答案。失败的子任务也要在汇总中说明。

### 关键设计决策

**子任务之间怎么传递信息？** 把依赖任务的结果拼接成上下文字符串，传给后续任务的描述里。

**并行度怎么控制？** 设一个 `maxParallel`（如 2-3），避免同时跑太多子 Agent 把 API 限流打爆。

**死锁怎么处理？** 如果所有任务都未完成但没有可运行的（依赖图有环），要检测并报错。

**子 Agent 用什么工具？** 可以传一个 `toolsFilter` 限制子 Agent 只能用部分工具。简单起见也可以用全部工具。

### 实现步骤清单

1. 定义 SubTask、SubTaskResult 类型
2. 写任务分解器（专门 prompt + JSON 解析）
3. 写子 Agent 执行器（复用 runAgent + 独立上下文）
4. 写编排器（拓扑排序 + 有限并行 + 依赖上下文传递）
5. 写结果汇总器（专门 prompt 汇总）
6. 在 CLI 加子代理命令

### 验收标准

- [ ] 复杂任务能正确分解为 2+ 个子任务
- [ ] 无依赖的子任务能并行执行
- [ ] 有依赖的子任务等前置完成后再跑
- [ ] 汇总结果包含所有子任务的关键信息
- [ ] 单个子任务失败不会整体崩溃，汇总中能看到失败原因

## 写在最后

### 核心建议

1. **先做 Eval，建立基线**——这是你所有后续改动的度量衡
2. **不要贪多**——每个子阶段做完、跑通、验收过了，再进下一个
3. **多 Provider 是地基**——后面的可观测性、子代理都建在它上面
4. **成本意识**——跑评测、跑子代理都要花钱，设好上限

- 插件系统（让用户扩展工具和 Provider）
- RAG（代码库向量化检索）
- 自动修复（Agent 自己跑测试、自己改 bug）
